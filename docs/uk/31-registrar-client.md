# 9.1 Клієнт реєстрації

> [!NOTE]
> У SEMS немає реєстратора. Він є *клієнтом* реєстратора — реєструється сам, як це робить
> телефон, щоб проксі знав, куди слати для нього дзвінки. Ця інверсія збиває з пантелику
> ([1.1](01-introduction.md)): у цьому обміні медіа-сервер є абонентом, а не сервером.

## Навіщо медіа-серверу взагалі реєструватись

Три ситуації:

**Немає проксі взагалі.** `doc/Howtostart_noproxy.txt` описує реєстрацію SEMS на публічному
SIP-сервісі рівно так, як це зробив би софтфон. Досить, щоб спробувати сервіс; недосить для
будь-чого, що потребує даних абонента.

**Вихідні транки.** SEMS дзвонить у бік оператора, який чекає реєстрації, перш ніж прийме
дзвінки.

**Шлюзи за NAT.** Реєстрація тримає прив'язку відкритою, щоб дальній бік міг дотягнутись.

## `AmSIPRegistration`

```cpp
struct SIPRegistrationInfo {
  string domain;
  string user;
  string name;
  string auth_user;
  string pwd;
  string proxy;
  string contact;
};
```

Зверніть увагу: `user` і `auth_user` — окремі поля. Ідентичність, під якою ви реєструєтесь, і
ідентичність, під якою автентифікуєтесь, часто різні — транк, зареєстрований як пілотний номер,
але автентифікований іменем акаунта — і плутанина між ними є класичною помилкою першого дня.

Сам об'єкт реєстрації — невелика машина станів навколо діалогу:

```cpp
class AmSIPRegistration
{
  string sess_link;
  ...
  void setRegistrationInfo(const SIPRegistrationInfo& _info);
  void setSessionEventHandler(AmSessionEventHandler* new_seh);
  void setExpiresInterval(unsigned int desired_expires);

  bool doRegistration();
  bool doUnregister();

  bool timeToReregister(time_t now_sec);
  bool registerExpired(time_t now_sec);
  void onRegisterExpired();
  void onRegisterSendTimeout();
  bool registerSendTimeout(time_t now_sec);

  void onSendRequest(AmSipRequest& req, int& flags);
  void onSendReply(const AmSipRequest& req, AmSipReply& reply, int& flags);
  void onSipReply(const AmSipRequest& req, ...);

  bool active;
  bool remove;
  bool waiting_result;
  bool unregistering;

  enum RegistrationState { ... };
  RegistrationState getState();
  bool getUnregistering();
};
```

Три деталі варті витягу.

**`setSessionEventHandler()` — це те, як відбувається автентифікація.** Реєстратор майже завжди
челенджить `401`, і замість реалізовувати digest тут, реєстрація чіпляє `uac_auth` як обробник
подій сесії ([4.4](15-session-event-handlers.md)). На челендж відповідає код, що нічого не знає
про реєстрацію, а `AmSIPRegistration` `401` навіть не бачить — обробник повертає `true` і ковтає
його.

**Таймаутів два, і вони різні.** `registerExpired()` — це «прив'язка, яку ми тримаємо,
скінчилась»; `registerSendTimeout()` — «ми надіслали REGISTER і не отримали відповіді».
Реєстратор, що тихо зник, — це інша відмова, ніж той, що відповідає й дає прив'язці протухнути,
і об'єкт відстежує їх окремо.

**`timeToReregister()` спрацьовує до спливання, а не в момент.** Оновлення, надіслане в дедлайн і
доставлене із запізненням, дає вікно без прив'язки. Стандартна практика — оновлювати на якійсь
частці інтервалу, і `setExpiresInterval()` є *бажаним* строком: реєстратор може дати менше, і
саме надане значення використовують таймери.

`sess_link` — це local tag сесії, яку треба повідомити ([2.2](03-event-system.md)), щоб застосунок
дізнавався про підйом чи падіння своєї реєстрації, а не опитував.

Реєстрації користуються діалогами, не будучи дзвінками, і саме тому рівень діалогів розділяє
`AmBasicSipDialog` і `AmSipDialog` ([3.5](11-dialog-layer.md)).

## Три застосунки

| Застосунок | Реєстрації беруться | Для чого |
|---|---|---|
| `reg_agent` | З конфігураційного файлу | Фіксований набір транків |
| `db_reg_agent` | З бази даних | Тисячі, що змінюються в рантаймі |
| `registrar_client` | З RPC / інших модулів | Програмне керування |

`db_reg_agent` — той, що масштабується, і його проблеми найцікавіші. Десять тисяч реєстрацій із
інтервалом у хвилину — це 167 REGISTER за секунду назавжди, а якби всі вони завантажились
одночасно, то й падали б в одну й ту саму секунду щохвилини. Будь-яке серйозне розгортання — це
вправа з розмазування цього навантаження, тобто задача планування, а не SIP.

`registrar_client` відкриває DI-інтерфейс ([8.1](28-rpc-architecture.md)), тож реєстрації можна
додавати й прибирати в рантаймі зовнішньою системою. У зразковій конфігурації `xmlrpc2di` він
фігурує як кандидат на `direct_export`:

```
# direct_export=di_dial;registrar_client
```

> [!WARNING]
> Це означає, що неавтентифікований RPC-клієнт може **додати** реєстрацію — сказавши оператору,
> що ця машина тепер є призначенням для номера — і **прибрати** її, тихо знявши транк. Порти RPC
> не мають автентифікації ([8.1](28-rpc-architecture.md)); це одна з конкретних причин, чому це
> важить ([10.1](37-security-surface.md)).

## Для контрасту: кешування реєстрацій

`RegisterCache` у SBC ([6.5](23c-sbc-call-control.md)) є дзеркальним відображенням, і його варто
назвати тут, щоб їх не плутали:

| | `AmSipRegistration` | `RegisterCache` |
|---|---|---|
| Напрямок | SEMS реєструється **назовні** | SEMS поглинає реєстрації **всередину** |
| Роль | Клієнт | Радше сервер, перед справжнім реєстратором |
| Стан | Наші прив'язки деінде | Чужі прив'язки в нас |
| Ким вживається | `reg_agent`, `db_reg_agent`, `registrar_client` | `cc_registrar` |

Один SBC часто робить і те, і те: поглинає абонентські реєстрації на абонентському боці й
реєструється в оператора на транковому.

## Експлуатація

**Слідкуйте за флапом.** Реєстрація, що постійно спливає й реєструється знову, зазвичай означає,
що наданий строк коротший за очікуваний, або що `timeToReregister()` змагається з мережею.

**Мовчазний реєстратор гірший за той, що відмовляє.** Виявляє це шлях `registerSendTimeout()`;
без сесії, зв'язаної через `sess_link`, цього може ніхто не помітити, доки не почнуть падати
дзвінки.

**Облікові дані лежать у конфігурації.** `SIPRegistrationInfo::pwd` — звичайний рядок,
прочитаний із файлу чи бази. Права на цей файл є частиною вашої безпекової позиції
([10.3](39-security-hardening.md)).
