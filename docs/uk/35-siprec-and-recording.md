# 9.5 SIPREC і запис

> [!NOTE]
> У SEMS є два непов'язані види запису: **захоплення пакетів** для дебагу і **запис дзвінків** із
> бізнесових причин. Вони використовують різний код, дають різні артефакти й підпадають під різні
> правила. Цей розділ покриває обидва й старанно тримає їх окремо.

## Захоплення пакетів: `msg_logger`

Дебажний бік — це невеликий, добре факторизований інтерфейс у `core/sip/`:

```cpp
class msg_logger
  : public atomic_ref_cnt
{
public:
  virtual int log(const char* buf, int len,
		  sockaddr_storage* src_ip,
		  sockaddr_storage* dst_ip,
		  cstring method, int reply_code=0)=0;
};

class file_msg_logger
  : public msg_logger
{
protected:
  exclusive_file* excl_fp;
  int write(const void *buf, int len);
  int writev(const struct iovec *iov, int iovcnt);
  virtual int write_file_header() = 0;
public:
  int open(const char* filename);
  ...
};
```

Один метод: ось байти, ось звідки й куди вони йшли, ось чим вони були. Усе решта — реалізація.

Три речі варті уваги.

**Він рахує посилання** (`atomic_ref_cnt`, [2.3](04-memory-and-ownership.md)), бо логер спільний:
той самий може бути причеплений і до діалогу, і до обох медіа-потоків B2B-пари
([6.2](22-b2b-media.md)).

**`write_file_header()` є чисто віртуальним у файловому варіанті**, і саме це робить можливим
`pcap_logger`: pcap потребує глобального заголовка перед першим пакетом, і базовий клас кличе це
один раз при відкритті.

**Він вживає `writev()` і `exclusive_file`.** Scatter-gather запис уникає складання буфера на
кожен пакет, а ексклюзивний файл дає раду конкурентним писакам — кілька сесій можуть писати в
один файл без пошкодження від перемішування.

Реалізації: `pcap_logger` пише стандартний pcap, читаний Wireshark'ом; `cf_msg_logger` пише
текстовий формат.

Причепити логер — це один виклик, і він працює на обох рівнях:

```cpp
    void setLogger(msg_logger *logger) { a.setLogger(logger); b.setLogger(logger); }
```

на `AudioStreamPair` і `RelayStreamPair` ([6.2](22-b2b-media.md)), тож SIP **і** медіа одного
дзвінка лягають в один pcap.

> [!IMPORTANT]
> Це і є точка розширення для HEP. Протокол Homer є транспортом рівно для тієї трійки, яку
> `msg_logger::log()` уже отримує: навантаження, джерело, призначення, тип повідомлення.
> Реалізація HEP була б новим підкласом `msg_logger`, що шле UDP замість писати файл, і не
> потребувала б змін ніде більше. Це, і чого бракує сьогодні, — [13.2](48-hep-and-capture.md).

## Запис дзвінків: SIPREC

SIPREC (RFC 7865 і 7866) — стандартний спосіб записувати дзвінки, не навчаючи кожен ендпоінт про
запис. **Session Recording Client** форкає медіа на **Session Recording Server**, із метаданими,
що описують, хто є хто.

SEMS постачає обидві половини:

| Компонент | Роль |
|---|---|
| `apps/sbc/call_control/siprec` | **Клієнт** — SBC, що форкає медіа на рекордер |
| `apps/siprec_srs` | **Сервер** — приймає форкнуте медіа й метадані |

Це незвично й корисно. Можна записувати, маючи SEMS у розриві, або використати SEMS як рекордер
для чужого SBC, або і те, і те.

### Бік клієнта

`cc_siprec` — модуль call control ([6.5](23c-sbc-call-control.md)), і він висить на гачку «на
кожен пакет»:

```cpp
    virtual void onAfterRTPRelay(SBCCallLeg *call, AmRtpPacket* p, ...);
```

Це єдине місце в SBC, де модуль бачить окремі RTP-пакети, і це рівно те, що потрібно форку: взяти
щойно релейований пакет і надіслати копію деінде. Зверніть увагу: отже, це працює **в режимі
релею** — запис не змушує дзвінок переходити на повний медіа-шлях
([9.4](34-rtp-mux-and-relay.md)), і саме це робить запис трафіку SBC доступним за ціною.

> [!WARNING]
> `onAfterRTPRelay()` виконується на потоці RTP-приймача ([5.2](17-rtp-stream.md)). Блокуюча
> відправка там стопорить пересилання пакетів для кожного релейованого дзвінка на цьому потоці.
> Скопіювати, покласти в чергу, повернутись.

Те, що це модуль call control, ще й означає, що *рішення* записувати є політикою: профіль або
інший модуль може вмикати його на кожен дзвінок окремо ([6.4](23b-sbc-profiles.md)).

### Бік сервера

```
apps/siprec_srs/
  SiprecSrs.cpp
  RtpReceiver.cpp
  Readme.siprec_srs.txt
```

Застосунок, що приймає сесії запису й пише отримані потоки. Його власний `RtpReceiver` окремий від
ядерного ([5.2](17-rtp-stream.md)), бо робота сервера запису вужча: прийняти багато потоків,
скорелювати їх із метаданими, записати.

Кореляція тут і є цікавим. Записаний дзвінок — це щонайменше два потоки, які треба
ідентифікувати як два напрямки однієї розмови і, зазвичай, змікшувати або зберегти стерео-парою.
SIPREC несе метадані рівно для цього: який учасник, який потік, який дзвінок.

## Як обирати

| Потреба | Вживайте |
|---|---|
| Дебаг проблеми сигналізації | `pcap_logger` на діалозі, дивитись у Wireshark |
| Дебаг аудіо | `pcap_logger` на медіа-потоках |
| Запис дзвінків із бізнесових причин | SIPREC — `cc_siprec` плюс рекордер |
| Запис, коли ви й так на медіа-шляху | Аудіо-ланцюжок ([9.3](33-msg-storage-and-voicemail.md)) |
| Слати сигналізацію в Homer | Сьогодні недоступно ([13.2](48-hep-and-capture.md)) |

## Два застереження

**Захоплення — це проблема місця на диску й приватності.** Увімкнути pcap-логування широко на
завантаженому сервері означає швидко забити диск, а ці файли містять вміст дзвінків і
ідентифікатори. Дебажне захоплення має бути точковим і короткочасним.

**Запис — це юридичне питання раніше, ніж технічне.** Згода, строки зберігання, шифрування й
контроль доступу різняться за юрисдикціями, і SEMS не дає нічого з цього — він дає механізм і
більше нічого. Хоч би якими були ваші зобов'язання, вони живуть у рекордері й у сховищі, а не тут
([10.1](37-security-surface.md)).
