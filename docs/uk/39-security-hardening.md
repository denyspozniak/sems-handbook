# 10.3 Hardening

> [!NOTE]
> Це практичний розділ: що налаштувати, що обмежити і що протестувати. Кожен пункт простежується
> до механізму, розібраного раніше — сенс тут у тому, щоб поставити їх у той порядок, у якому ви
> справді їх застосовуватимете.

## Скиньте привілеї

SEMS уміє змінити користувача й групу на старті, і типово **не робить цього**:

```c
# define DEFAULT_DAEMON_UID         ""
# define DEFAULT_DAEMON_GID         ""
```

Порожній рядок означає, що крок пропускається, тож сервер, запущений від root, лишається root,
доки ви не скажете інакше:

```
daemon_uid=sems
daemon_gid=sems
```

Реалізація в `core/sems.cpp` конвенційна й сувора до відмов:

```cpp
      if(setgid(gid)<0){
	ERROR("Cannot change GID to %i: %s.", gid, strerror(errno));
	goto error;
      }
      ...
      if(setuid(uid)<0){
	ERROR("Cannot change UID to %i: %s.", uid, strerror(errno));
	goto error;
      }
```

`goto error` — невдале скидання перериває старт, а не продовжує з привілеями. Це правильна
поведінка, і про неї варто знати, бо одруківка в імені користувача зупиняє сервер.

Спершу група, потім користувач — і це правильний порядок: після `setuid()` змінити групу вже не
можна.

```cpp
#if defined(__linux__)
    if(!AmConfig::DaemonUid.empty() || !AmConfig::DaemonGid.empty()){
      if (prctl(PR_SET_DUMPABLE, 1, 0, 0, 0) < 0) {
	WARN("unable to set daemon to dump core after setuid/setgid\n");
      }
    }
#endif
```

Linux скидає прапорець dumpable після зміни UID, тож дампи були б втрачені. SEMS його повертає.

> [!WARNING]
> Це означає, що **core-файли увімкнені після скидання привілеїв**, а core медіа-сервера містить
> аудіо дзвінків, SIP-заголовки, облікові дані й кеш ZRTP із пам'яті. Корисно для дебагу — і
> проблема захисту даних, якщо дампи лягають туди, де їх можна прочитати. Свідомо вирішіть, куди
> вказує `kernel.core_pattern` і хто може це читати.

Два наслідки скидання привілеїв:

**Порти нижче 1024 потребують допомоги.** Прив'язати 5060 нормально, але якщо потрібен
привілейований порт — беріть `CAP_NET_BIND_SERVICE`, а не лишайтесь root.

**Сирі сокети потребують `CAP_NET_RAW`** ([3.2](08-transport.md)). Опція `use_raw_sockets`
недоступна непривілейованому процесу без неї.

Обидва — це capabilities на бінарнику або в service-юніті, а не причини працювати від root.

## Біндьте свідомо

Кожен слухач має бути на інтерфейсі, який ви обрали:

```
#  sip_ip_intern=eth0
#  sip_port_intern=5060
#  media_ip_intern=eth0

#  sip_ip_extern=213.192.59.73
#  sip_port_extern=5060
#  media_ip_extern=213.192.59.73
```

Поділ `intern`/`extern` у зразковій конфігурації — це форма, яку варто копіювати: сигналізація й
медіа на названих інтерфейсах, із недовіреним боком, відділеним від довіреного. `sip_ip` приймає
й ім'я інтерфейсу замість адреси, що переживає зміну адреси.

І ті, що важать найбільше ([10.1](37-security-surface.md)):

- **XML-RPC (8090) і JSON-RPC (7080) — на loopback або керуючий інтерфейс.** Вони не мають
  автентифікації і дають повний контроль над процесом.
- **UDP-порт `monitoring` — так само.**

## Виставте ліміти

```
session_limit="1000;503;Server overload"
cps_limit="100;503;Server overload"
options_session_limit="900;503;Warning, server soon overloaded"
```

Це hardening, а не тюнінг ([2.5](06-sizing-and-tuning.md)). Відмова з `503` не коштує нічого — ні
сесії, ні потоку, ні діалогу — а перевантажений медіа-сервер, що далі приймає, дає поганий звук
усім, хто вже на ньому.

`options_session_limit`, виставлений трохи нижче за `session_limit`, лишає keepalive-`OPTIONS`
відповідними, коли машина повна, тож проксі вище за течією бачить завантажений сервер, а не
мертвий, і може коректно його злити.

## Опустіть таймаути

| Параметр | Типово | Змінити на | Чому |
|---|---|---|---|
| `dead_rtp_time` | **300 с** | 30–60 с | П'ять хвилин на покинутий дзвінок ([5.2](17-rtp-stream.md)) |
| `tcp_idle_timeout` | **1 година** | Хвилини | Простійні з'єднання накопичуються проти ліміту fd ([3.2](08-transport.md)) |
| `tcp_connect_timeout` | 2 с | Підняти для далеких шляхів | Агресивно на перевантажених маршрутах |
| `max_shutdown_time` | 10 с | За потребою ваших дзвінків | Вікно drain ([2.4](05-lifecycle.md)) |

## Блоклист

`core/sip/tr_blacklist.*` тримає напрямки, що нещодавно відмовили:

```cpp
struct bl_addr: public sockaddr_storage
{
  unsigned int hash();
};

class blacklist_bucket
  : public bl_bucket_base
{
public:
  bool insert(const bl_addr& addr, unsigned int duration /* ms */, const char* reason);
  bool remove(const bl_addr& addr);
};
```

Хеш-таблиця адрес із тривалістю й причиною, що спливає через колесо таймерів
([3.4](10-transaction-layer.md)) і досяжна з транзакційного рівня через `STIMER_BL`.

Зрозумійте, чим це є: **реактивним і про напрямки.** Воно спиняє SEMS від довбання піра, що не
відповідає. Це не вхідний блоклист і воно нічого не робить з атакувальниками — блокування джерел
є справою проксі ([11.1](40-with-kamailio.md)) або фаєрвола.

## Права на файли

Усе чутливе є файлом, і права — увесь контроль ([10.1](37-security-surface.md)):

| Шлях | Містить |
|---|---|
| `sems.conf` і `plugin_config_path` | Паролі реєстрацій, доступи до бази |
| Тека плагінів | Код, що виконується в процесі ([7.1](24-plugin-architecture.md)) |
| ZRTP `cache_path`, `entropy_path` | Постійний ключовий матеріал ([9.6](36-zrtp-and-srtp.md)) |
| Записи й голосова пошта | Вміст дзвінків ([9.3](33-msg-storage-and-voicemail.md)) |
| Захоплення pcap | Вміст дзвінків і ідентифікатори ([9.5](35-siprec-and-recording.md)) |
| Core-дампи | Усе перелічене, з пам'яті |

Конфігурація читається лише користувачем демона; тека плагінів пишеться лише root'ом. Тека
плагінів, доступна на запис, — це віддалене виконання коду в кілька кроків.

## Фазинг

Мішень, що має значення, — парсер ([3.3](09-parser.md)): C поверх сирих вказівників, досяжний
однією неавтентифікованою датаграмою і довірений усім, що нижче за течією.

У `core/tests/` уже є каркас юніт-тестів (`fct.h`, `test_headers.cpp`, `test_extensions.cpp`,
`test_auth.cpp`, `test_amconfig.cpp`), і це точка старту, щоб обв'язати саме парсер, а не весь
сервер.

За пріоритетом:

1. **`sip_parser`** — ціла датаграма, зіпсована всіма способами.
2. **`skip_sip_msg_async`** — фреймінг потоку, особливо брехливий `Content-Length`
   ([3.3](09-parser.md)).
3. **`parse_uri`, `parse_from_to`, `parse_via`, `parse_cseq`** — структурні парсери.
4. **`AmSdp`** — досяжний кожним, хто може встановити дзвінок ([4.3](14-offer-answer.md)).
5. **`ParamReplacer`** — досяжний, якщо профіль підставляє вхід, контрольований атакувальником
   ([6.4](23b-sbc-profiles.md)).

Дві конкретні речі, на які варто дивитись, обидві вже названі в цій книзі:
`cstring::operator==` порівнює лише коротшу довжину й ніколи самі довжини ([3.3](09-parser.md)), а
фреймінг потоку довіряє `Content-Length`.

## Чеклист

**Процес**

- [ ] `daemon_uid` / `daemon_gid` виставлені; звірити через `ps -o user`
- [ ] Capabilities на бінарнику замість root, якщо потрібні
- [ ] `kernel.core_pattern` вказує в захищене місце

**Мережа**

- [ ] SIP прив'язаний до обраного інтерфейсу, а не до `0.0.0.0`
- [ ] Діапазон RTP звужений до реальної конкурентності ([10.2](38-security-media.md))
- [ ] Фаєрвол відповідає цьому діапазону й цим пірам
- [ ] Порти RPC лише на loopback або керуючому інтерфейсі
- [ ] UDP-порт `monitoring` так само

**Конфігурація**

- [ ] `session_limit`, `cps_limit`, `options_session_limit` виставлені
- [ ] `dead_rtp_time` опущений із 300 с
- [ ] `tcp_idle_timeout` опущений із години
- [ ] `exclude_payloads` звужений до кодеків, які ви приймаєте
- [ ] `application=` не контролюється викликачем на недовіреному інтерфейсі
  ([4.2](13-session-container-and-factories.md))
- [ ] Профілі SBC не маршрутизують за невалідованим `$H(...)` ([6.4](23b-sbc-profiles.md))

**Файли**

- [ ] Конфігурація читається лише користувачем демона
- [ ] Тека плагінів не пишеться користувачем демона
- [ ] Записи, голосова пошта й захоплення на захищеному сховищі
- [ ] Кеш ZRTP захищений, якщо вживається

**Архітектура**

- [ ] Проксі попереду робить автентифікацію, обмеження швидкості й блоклисти
  ([11.1](40-with-kamailio.md))
- [ ] SEMS недосяжний напряму з інтернету
