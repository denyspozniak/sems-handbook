# 5.2 RTP-потік

> [!NOTE]
> `AmRtpStream` — найбільший і найбагатший на опції клас медіа-площини, бо мусить задовольнити
> двох дуже різних замовників: медіа-сервер, який декодує аудіо, і SBC, який пересилає пакети
> недоторканими. Обидва живуть в одному класі й розрізняються прапорцем `relay_enabled`.

## Прийом: libevent, а не блокуючий цикл

RTP-приймач збудований не за схемою «потік на сокет у циклі `recvfrom`», якої можна було б
очікувати. Це цикл подій:

```cpp
#include <event2/event.h>

class AmRtpReceiverThread
  : public AmThread
{
  struct StreamInfo
  {
    AmRtpStream* stream;
    struct event* ev_read;
    AmRtpReceiverThread* thread;
    ...
  };
  ...
};
```

Кожен потік реєструє подію читання на своєму сокеті; libevent мультиплексує тисячі сокетів на
один потік. Саме тому `rtp_receiver_threads` типово дорівнює **1** (`NUM_RTP_RECEIVERS`), і цього
зазвичай достатньо: на пакет потік робить майже нічого — читає, визначає потік-власника і або
кладе пакет для медіа-процесора, або одразу релеїть.

> [!IMPORTANT]
> Коментар над `relay_stream` каже це прямо:
> ```cpp
>   /** pointer to relay stream.
>       ... or by the AmRtpReceiver thread while relaying!  */
> ```
> **У режимі релею пакет не доходить до медіа-процесора взагалі.** Він пересилається просто з
> потоку приймача. Ось чому RTP-релей у SEMS дешевий: без декодування, без джитер-буфера, без
> тика 10 мс, без копіювання на тик — читання й запис на тому самому потоці
> ([9.4](34-rtp-mux-and-relay.md)).

## Адреси, порти й утримання

```cpp
  unsigned short     r_port;
  unsigned short     r_rtcp_port;
  unsigned short     l_port;

  bool           r_ssrc_i;

  /** symmetric RTP & RTCP */
  bool           passive;
  bool           passive_rtcp;

  /** mute && port == 0 */
  bool           hold;
  bool           remotehold;

  bool           begin_talk;
  bool           monitor_rtp_timeout;
  bool           receiving;
  bool           mute;
  bool           force_receive_dtmf;
  bool           active;
```

Локальний порт береться з налаштованого діапазону ([2.5](06-sizing-and-tuning.md)); віддалена
адреса й порт — із погодженого SDP ([4.3](14-offer-answer.md)).

Коментар над `hold` — `/** mute && port == 0 */` — є точним визначенням. Утримання не є режимом;
це заглушення плюс анонс нульового порту, тобто рівно те, що каже SDP. `remotehold` —
дзеркало: дальній бік поставив на утримання *нас*.

`mute`, `receiving` і `force_receive_dtmf` — три перемикачі, які `AmSession` віддає напряму
([4.1](12-amsession.md)). Вони незалежні: заглушений потік усе одно приймає, а
`force_receive_dtmf` пропускає події RFC 2833 навіть коли аудіо інакше ігнорується — саме це
змушує працювати «натисніть клавішу, щоб говорити», поки канал заглушений.

## Симетричний RTP

```cpp
  /** handle symmetric RTP/RTCP - if in passive mode, update raddr from rp */
  void handleSymmetricRtp(struct sockaddr_storage* recv_addr, bool rtcp);
```

У режимі `passive` потік дізнається віддалену адресу з першого пакета, що приїхав, а не довіряє
SDP. Це стандартний обхід NAT: ендпоінт за NAT анонсує в SDP свою приватну адресу, але пакети,
що доходять до вас, несуть публічну — і саме туди мають іти відповіді.

```cpp
  /** ping the remote side, to open NATs and enable symmetric RTP */
```

Пара до цього — надіслати пакет заздалегідь, щоб NAT-прив'язка існувала ще до того, як дальній
бік спробує дотягнутись. Разом ці дві поведінки й становлять більшість того, що дозволяє SEMS
працювати за NAT без зовнішнього помічника.

> [!WARNING]
> Симетричний RTP — це ще й поверхня атаки. Потік у режимі `passive` перенаправляє власне
> вихідне аудіо на будь-яку адресу, з якої нібито прийшов пакет, тож атакувальник, здатний
> вгадати пару портів і підробити джерело, може викрасти напрямок аудіо. Це сімейство проблем
> RTP bleed; пом'якшення і те, до чого тут `r_ssrc_i`, — у [10.2](38-security-media.md).

## Режим релею

Конфігурація релею — це вже маленька власна мова:

```cpp
  /** if relay_stream is initialized, received RTP is relayed there */
  bool            relay_enabled;
  bool            relay_raw;
  AmRtpStream*    relay_stream;
  /** control transparency for RTP seqno in RTP relay mode */
  bool            relay_transparent_seqno;
  /** control transparency for RTP ssrc in RTP relay mode */
  bool            relay_transparent_ssrc;
  /** filter RTP DTMF (2833 / 4733) in relaying */
  bool            relay_filter_dtmf;
  ...
  PayloadMask     relay_payloads;
```

| Прапорець | Дія |
|---|---|
| `relay_enabled` | Пересилати прийнятий RTP у `relay_stream`, а не декодувати |
| `relay_raw` | Пересилати датаграму недоторканою, разом із заголовками |
| `relay_transparent_seqno` | Зберігати оригінальні порядкові номери, а не перенумеровувати |
| `relay_transparent_ssrc` | Зберігати оригінальний SSRC, а не підставляти власний |
| `relay_filter_dtmf` | Викидати payload'и RFC 2833/4733 з релейованого потоку |
| `relay_payloads` | 128-бітна маска того, які типи payload дозволено релеїти |

Два прапорці прозорості — справжнє рішення щодо сумісності. Прозорі SSRC і порядкові номери
роблять релей невидимим, чого деякі ендпоінти вимагають; переписування робить дві ноги
незалежними, чого хочеться, якщо ноги можуть перевстановлюватись окремо. Універсально правильної
відповіді немає — тому обидва існують як перемикачі.

`PayloadMask` — 128-бітна бітова карта з перевіркою діапазону, яка логує баг, а не довіряє тому,
хто викликав:

```cpp
    bool get(unsigned char payload_id) {
      if (payload_id > 127) { ERROR("BUG: payload_id out of range\n"); return false; }
      return (bits[payload_id / 8] & (1 << (payload_id % 8)));
    }
```

Вона вирішує на кожен тип payload, чи пересилати пакет — тож SBC може релеїти аудіо, термінуючи
DTMF, або пропускати кодек, якого не розуміє, блокуючи той, який відмовляється нести
([6.2](22-b2b-media.md)).

## Відправка

```cpp
  int send( unsigned int ts, ... );
  int send_raw( char* packet, unsigned int length );
  int compile_and_send( const int payload, bool marker, ... );
```

Три рівні. `compile_and_send()` будує RTP-заголовок навколо payload'а — звичайний шлях із
аудіо-ланцюжка. `send()` — закодований шлях. `send_raw()` пише байти як є, і саме ним
користується `relay_raw`.

Параметр `marker` у `compile_and_send()` — це маркерний біт RTP: він виставляється на першому
пакеті сплеску мовлення, і саме так `begin_talk` доходить до дроту, а playout-буфер приймача
дізнається, що треба ресинхронізуватись ([5.5](20-dtmf-and-jitter.md)).

## Таймаути й живість

```cpp
  bool monitor_rtp_timeout;
```

На кожен потік окремо, щоб потік, який законно очікує тишу — нога запису, потік на утриманні —
міг відмовитись. Поріг — `dead_rtp_time`, типово **300 секунд**
([2.5](06-sizing-and-tuning.md)).

Це єдиний механізм, що вивільняє дзвінок, чий дальній бік зник без `BYE`. П'ять хвилин — довго,
щоб тримати сесію, потік і пару портів заради дзвінка, якого вже немає; зменшити зазвичай
правильно.

## Порти як ресурс

Кожен потік бере пару портів — RTP на парному, RTCP на наступному. За зразкового діапазону
10000–60000 це 25 000 пар, тож порти рідко бувають першою стелею
([2.5](06-sizing-and-tuning.md)).

Важать вони з іншої причини: цей діапазон є вашим правилом фаєрвола і вашою відкритою поверхнею.
Діапазон, значно ширший за реальну конкурентність, — це 50 000 відкритих UDP-портів, що
рекламують себе кожному, хто сканує. Звузьте до того, що справді потрібно
([10.2](38-security-media.md)).
