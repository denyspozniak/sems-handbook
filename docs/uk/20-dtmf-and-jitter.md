# 5.5 DTMF і джитер

> [!IMPORTANT]
> Дві на вигляд не пов'язані проблеми ділять розділ, бо ділять причину: мережа доставляє аудіо
> запізно, не в тому порядку або взагалі ні, а натискання клавіші має три різні способи приїхати.
> І те, і те — це медіа-площина, що компенсує речі, яких вона не контролює.

## Три шляхи, якими приїжджає цифра

```cpp
  enum EventSource { SOURCE_RTP, SOURCE_SIP, SOURCE_INBAND, SOURCE_DETECTOR };
```

| Джерело | Механізм | Детектор |
|---|---|---|
| `SOURCE_RTP` | Іменовані події RFC 2833/4733 в RTP-потоці | `AmRtpDtmfDetector` |
| `SOURCE_SIP` | SIP-запит `INFO` по шляху сигналізації | `AmSipDtmfDetector` |
| `SOURCE_INBAND` | Справжні тони DTMF, змішані в аудіо | `AmInbandDtmfDetector` |
| `SOURCE_DETECTOR` | Мітка на події, яку врешті віддають застосунку | — |

Медіа-сервер не може обрати за викликачів, тож реалізує всі три й нормалізує їх. Ця нормалізація
і є `AmDtmfDetector`, і вона більша за оператор switch.

## Чому розпізнаванню потрібна машина станів

```cpp
class AmKeyPressSink {
  ...
  virtual void registerKeyPressed(int event, Dtmf::EventSource source,
                                  bool has_eventid=false, unsigned int event_id=0) = 0;
  virtual void registerKeyReleased(int event, Dtmf::EventSource source, ...) = 0;
  virtual void flushKey(unsigned int event_id) = 0;
};
```

Натискання й відпускання розділені, бо цифра має тривалість, і застосункам вона потрібна:
«натисніть і утримуйте 5, щоб записати» — реальна вимога.

Складне тут те, що три джерела перекриваються. Ендпоінт може слати RFC 2833 *і* лишати тони в
аудіо, тож те саме натискання приїжджає двічі. Події RFC 2833 ще й шлються надлишково за
задумом — та сама подія повторюється в кількох пакетах, щоб втрата її не проковтнула. Без
дедуплікації одне натискання стає трьома-чотирма.

`event_id` і `flushKey()` — це і є дедуплікація. Події, що несуть ідентифікатор, корелюються, а
`flushKey()` закриває одну з них, щойно вона остаточно завершилась. `AmDtmfDetector` оголошує три
детектори джерел друзями, щоб ті годували його напряму:

```cpp
  friend class AmSipDtmfDetector;
  friend class AmRtpDtmfDetector;
  friend class AmInbandDtmfDetector;
```

До застосунку результат доходить одним чистим колбеком ([4.1](12-amsession.md)):

```cpp
  virtual void onDtmf(int event, int duration);
```

## Inband-розпізнавання

```cpp
  enum InbandDetectorType { SEMSInternal, SpanDSP };

class AmSemsInbandDtmfDetector { ... };
class AmSpanDSPInbandDtmfDetector { ... };
```

Дві реалізації, обираються через `setInbandDetector()`. Внутрішня — детектор тонів у стилі
Ґьорцеля: дешево й достатньо. SpanDSP — зріла й значно точніша DSP-бібліотека, ціною залежності
й більшого CPU.

> [!WARNING]
> Inband-розпізнавання працює лише на аудіо, яке SEMS справді декодує. У режимі релею
> ([5.2](17-rtp-stream.md)) пакети не доходять до аудіо-ланцюжка, тож inband-DTMF невидимий — а
> стиснутий кодек міг і так спотворити тони до невпізнанності. Якщо DTMF важливий і ви не можете
> зобов'язати всіх до RFC 2833, чистий релей вам не підходить.

## Playout-буфер

Прийняте аудіо приїжджає не в такт тому тику 10 мс, який хоче його спожити
([5.1](16-media-processor.md)). Playout-буфер і є мостом між двома годинниками:

```cpp
class AmPlayoutBuffer
{
  unsigned int last_ts;
  unsigned int sample_rate;
  unsigned int recv_offset;
  ...
  void buffer_put(unsigned int ts, ShortSample* buf, unsigned int len);
  void buffer_get(unsigned int ts, ShortSample* buf, unsigned int len);
  virtual void write(u_int32_t ref_ts, u_int32_t ts, int16_t* buf, u_int32_t len, bool begin_talk);
};
```

Пакети кладуться зі своїми RTP-мітками; медіа-процесор бере семпли за системною міткою.
`recv_offset` — це відображення між двома годинниками, а `begin_talk` — маркерний біт RTP
([5.2](17-rtp-stream.md)) — каже ресинхронізуватись, бо новий сплеск мовлення може початись
після довільної паузи.

Три реалізації:

| Клас | Стратегія |
|---|---|
| `AmPlayoutBuffer` | Фіксована. Проста, передбачувана затримка |
| `AmAdaptivePlayout` | Підлаштовується під виміряний джитер, міняючи затримку на втрати |
| `AmJbPlayout` | Звичайний джитер-буфер |

Найцікавіші константи живуть в адаптивному:

```cpp
#define ORDER_STAT_WIN_SIZE  35
#define ORDER_STAT_LOSS_RATE 0.1

#define EXP_THRESHOLD 20
#define SHR_THRESHOLD 180

#define WSOLA_START_OFF  10 * sample_rate / 1000
#define WSOLA_SCALED_WIN 50

#define TEMPLATE_SEG   10 * sample_rate / 1000
```

Він тримає **порядкову статистику** у вікні з 35 пакетів і цілиться в частку втрат 0.1 — тобто
розмірює буфер так, щоб близько 10% пакетів вважались запізнілими, свідомо міняючи трохи втрат
на меншу затримку. `EXP_THRESHOLD` і `SHR_THRESHOLD` — це гістерезис: рости швидко (20),
стискатись повільно (180), бо запізно вирости коштує чутних провалів, а зарано стиснутись не
коштує майже нічого.

**WSOLA** — Waveform Similarity Overlap-Add — це те, як він міняє глибину буфера без клацання.
Наївно викинути чи повторити 10 мс аудіо чутно; WSOLA знаходить схожий сегмент форми хвилі й
склеює саме там, тож підлаштування нечутне. Це і параметризують `TEMPLATE_SEG` та
`WSOLA_SCALED_WIN`.

## Приховування втрат

```cpp
#define PLC_MAX_SAMPLES (4*20*sample_rate / 1000)
```

Чотири пакети — 80 мс — це стеля того, як довго приховування синтезуватиме. За нею з'єднання не
страждає від втрат, а зламане, і вигадати секунду аудіо було б гірше за тишу.

Приховування відбувається на двох рівнях. Кодек може реалізувати `amci_plc_t` і приховувати у
власній області, що завжди краще ([5.4](19-codecs-and-plugins.md)). Якщо ні — `LowcFE.cpp` є
загальним малозатратним приховувачем стирання фреймів, який працює на лінійних семплах для
будь-якого кодека.

## Тюнінг

**Фіксований буфер для передбачуваних мереж, адаптивний для інтернету.** Усередині дата-центру
адаптивна машинерія додає складності заради джитера, якого немає.

**Глибший буфер міняє затримку на якість**, і немає налаштування, що уникає цього обміну — є
лише вибір, де саме на ньому сидіти. Цільова частка втрат 0.1 — це думка коду про те, де це;
нога запису цілком законно може хотіти зовсім іншого.

**Віддавайте перевагу DTMF за RFC 2833** і узгоджуйте `telephone-event` у SDP.
Inband-розпізнавання коштує CPU на кожному потоці, ненадійне крізь стиснуті кодеки й не працює
взагалі в режимі релею.

**Дивіться на втрати й приховування разом.** Стабільне приховування означає втрати, які буфер
ховає від ваших користувачів, але не від якості дзвінка — а цифри лежать у RTCP
([1.2](01b-sip-media-primer.md)).
