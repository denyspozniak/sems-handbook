# 13.5 Диспатчинг на групу пірів

> [!IMPORTANT]
> Це та прогалина, де чесна відповідь зазвичай — **«покладіть це в проксі»**. Вибору напрямку в
> SEMS більше, ніж припускають — включно зі справжнім паралельним форкінгом — і все одно немає
> списку пірів зі станом здоров'я. Цей розділ викладає і те, і те, і випадки, коли відповідь про
> проксі неправильна.

## Що є, а це більше, ніж здається

### Статичний next hop

`SBCCallProfile` ([6.4](23b-sbc-profiles.md)) несе ту саму ручку з чотирьох частин, що й рівень
діалогів ([3.5](11-dialog-layer.md)):

```cpp
  string next_hop;
  bool next_hop_1st_req;
  bool patch_ruri_next_hop;
  bool next_hop_fixed;
  string aleg_next_hop;

  string outbound_proxy;
  bool force_outbound_proxy;
```

Оскільки поля профілю є шаблонами, що обчислюються на кожен дзвінок
([6.4](23b-sbc-profiles.md)), `next_hop` можна обчислити — із заголовка, зі змінної, яку виставив
модуль call control, або з regex-мапи:

```
next_hop=$M(carriers/$rd)
```

Це таблиця пошуку. Статична, з конфігурації, без рантайм-стану.

### DNS SRV і NAPTR

`core/sip/resolver.*` — повноцінний резолвер за RFC 3263 ([3.2](08-transport.md)):

| Тип | Запис | Дає |
|---|---|---|
| `dns_srv_entry` | SRV | **Пріоритет і вагу** |
| `dns_naptr_entry` | NAPTR | Перевагу транспорту |
| `dns_handle` | — | Курсор по списку результатів |

Тож R-URI, що резолвиться через SRV, уже дає впорядкований зважений список цілей. Це і є група
пірів, виражена в DNS.

### Failover між розв'язаними адресами

```cpp
    // Transport address failover timer:
    // - used to cycle throught multiple addresses
    //   in case the R-URI resolves to multiple addresses
    STIMER_M,
```

Таймер M, типово `B/4` = **8 секунд** ([3.4](10-transaction-layer.md)), просуває курсор
`dns_handle`, коли ціль не відповіла.

> [!NOTE]
> Таймер B — це 32 секунди, а таймер M — 8, тож **буде спробувано щонайбільше чотири адреси**,
> перш ніж транзакція здасться. Якщо ви сподівались, що SRV дасть вам великий пул із витонченим
> обходом, — не дасть.

### Паралельний форкінг

Той, який більшість не помічає ([6.3](23-sbc.md)):

```cpp
    /** List of legs which can be connected to this leg, it is valid for A leg until first
     * 2xx response which moves the A leg to Connected state and terminates all
     * other B legs. */
    std::vector<OtherLegInfo> other_legs;
```

A-нога SBC може мати **багато B-ніг одночасно**. Подзвонити на три напрямки паралельно; перша
`2xx` перемагає, решта термінується. `addCallee()` кличеться на кожного кандидата
([6.3](23-sbc.md)).

Це не безкоштовно: кожен кандидат несе власний `AmB2BMedia` і власну пару портів
([6.2](22-b2b-media.md)), що звільняються, коли переможець відповів.

### Serial fork — як хук

```cpp
     * Redefine to implement serial fork or handle redirect. */
```

`apps/sbc/CallLeg.h:211`. Послідовний форкінг не реалізований; задокументована точка розширення,
щоб його реалізувати.

## Чого бракує

| | `dispatcher` у Kamailio | SEMS |
|---|---|---|
| Список пірів | Набори, завантажувані й перезавантажувані | Лише те, що поверне DNS, або один `next_hop` |
| Пробінг здоров'я | Активні `OPTIONS` до кожного піра | **Немає** |
| Рантайм-стан | Up / down / probing на кожного піра | **Немає** |
| Алгоритми | Хеш, round-robin, зважений, за навантаженням | Лише пріоритет і вага з DNS |
| Адмін-контроль | Увімкнути/вимкнути піра в рантаймі по RPC | **Немає** |
| Виявлення відмови | До спроби — пір уже відомий як мертвий | Після спроби, на 8 чи 32 секундах |

Останній рядок і є суттєвою різницею. `dispatcher` **знає**, що пір лежить, до того як щось
надіслати; SEMS дізнається, дочекавшись таймауту. На пірі, що відмовляє тихо, це коштує 32
секунди сесії й потоку на кожен дзвінок ([2.5](06-sizing-and-tuning.md)).

`tr_blacklist` ([10.3](39-security-hardening.md)) — найближче до цього, і воно реактивне:
напрямків, що нещодавно відмовили, певний час уникають. Воно вчиться на відмовах, а не запобігає
їм.

## Чому проксі зазвичай правий

Вибір піра є **маршрутним** рішенням, а маршрутизація — це те, для чого проксі й існує
([1.1](01-introduction.md), [11.1](40-with-kamailio.md)):

**Там це дешево.** Проксі оглядає запит, не створюючи сесії ([2.1](02-thread-model.md)). SEMS
платить сесією й потоком, перш ніж узагалі щось вирішить.

**Пробінг коштує однаково для всіх.** Один проксі, що шле `OPTIONS` двадцяти операторам, — це
двадцять транзакцій. Двадцять інстансів SEMS, кожен пробінгує двадцять операторів, — це
чотириста, і кожен інстанс має власну, можливо суперечливу, думку.

**Стан хоче бути спільним.** «Оператор 3 лежить» має бути відомим один раз, а не перевідкриватись
кожним інстансом. Інстанси SEMS не ділять нічого ([11.2](41-topologies-and-ha.md)), тож класти це
нікуди.

**Yeti погоджуються.** Yeti збудували LCR, контроль навантаження й переносність номерів *над*
SEMS, а не всередині ([12.3](45-fork-yeti-switch.md)) — команда, що будувала операторський
комутатор на цьому коді, винесла маршрутизацію назовні, і це найсильніший наявний доказ.

## Коли він неправий

**Рішення після відповіді.** Обрати наступного кандидата на підставі того, що з'ясувалось *після*
відповіді на дзвінок — якість медіа, натиснута цифра, вивід розпізнавача — недоступне проксі, який
зійшов зі шляху. Це бачить лише B2BUA.

**Політика на ногу, що залежить від кандидата.** Різні кодеки, заголовки чи автентифікація на
кожен напрямок ([6.4](23b-sbc-profiles.md)) — це робота профілів, а профілі живуть у SEMS.

**Паралельний форкінг із медіа.** Дзвонити на три напрямки, граючи викликачу early media, — це
поведінка B2BUA, і механізм у SEMS уже є.

**У розгортанні немає проксі.** Якщо SEMS стоїть самостійно ([1.1](01-introduction.md)), логіці
просто нема куди піти.

## Якщо ви все одно це будуєте

Форма, що лягає на наявний код:

**Модуль call control, а не зміна ядра** ([6.5](23c-sbc-call-control.md)). `onInitialInvite()` —
місце, де обирається напрямок, і модуль може виставити глобальну змінну, яку профіль прочитає як
`$V(...)` ([6.4](23b-sbc-profiles.md)). Без патчів у ядрі, і можна вимкнути на кожен профіль.

**Пробінг на `AmPeriodicThread`** ([8.3](30-app-timers-and-events.md)), із `OPTIONS` через
`AmUAC::dialout()` ([4.2](13-session-container-and-factories.md)) і результатами в структурі, яку
читає шлях вибору.

**Стан, відкритий по DI** ([8.1](28-rpc-architecture.md)), щоб пірів можна було вмикати й вимикати
в рантаймі й дивитись стан — дзеркалячи те, що дає `dispatcher`.

**Паралельний форкінг через `addCallee()`**, коли кандидатів треба пустити наввипередки, а не
пробувати послідовно ([6.3](23-sbc.md)).

> [!WARNING]
> Пробінг — це фоновий потік із мережевим вводом-виводом в однопроцесному сервері
> ([2.1](02-thread-model.md)). Він не має права блокувати шлях вибору, а шторм проб на старті —
> двадцять пірів, усі одразу, з кожного інстансу — добрий спосіб отримати обмеження швидкості від
> власних операторів. Розтягуйте в часі.

## Рекомендація

**Беріть `dispatcher` Kamailio** для вибору пірів, пробінгу здоров'я й failover
([11.1](40-with-kamailio.md)). Це правильний компонент, він уже існує, і стан живе в одному місці.

**Беріть паралельний форкінг SEMS** для випадків, які може обслужити лише B2BUA — гонка кандидатів
із медіа або рішення після відповіді.

**Беріть regex-мапи `$M(...)`** для статичних маршрутних таблиць, яким не потрібен стан здоров'я
([6.4](23b-sbc-profiles.md)).

**Опустіть `dead_rtp_time` і виставте ліміти сесій**, щоб пір, який відмовляє тихо, коштував
менше, поки спливають таймери ([2.5](06-sizing-and-tuning.md)).

З чотирьох прогалин цієї частини саме тут відсутня функція найочевидніше відсутня *навмисно*. SEMS
є медіа-сервером ([1.1](01-introduction.md)); маршрутизації місце по сусідству.
