# 3.3 Парсер

> [!IMPORTANT]
> Парсер ніколи не копіює. Розібраний `sip_msg` — це набір вказівників у буфер, який щойно
> заповнив транспорт. Саме це робить його швидким, і це ж є джерелом найнебезпечнішого правила
> в `core/sip/`: **ніщо, похідне від `sip_msg`, не має права пережити його самого.**

## `cstring`

Усе тримається на структурі з двох полів:

```cpp
struct cstring
{
    const char*  s;
    unsigned int len;
    ...
};
```

Вказівник і довжина. Без алокації, без володіння, без термінатора. `To`, `From`, `Call-ID`,
R-URI, значення кожного заголовка — усе це `cstring`, що вказують у той самий приймальний буфер.
Розібрати повідомлення — це здебільшого пройти цей буфер один раз і записати зміщення.

Перехід у світ C++ явний, і саме там відбувається копіювання:

```cpp
#define c2stlstr(str) \
          string((str).s,(str).len)
#define stl2cstr(str) \
          cstring((char*)(str).c_str(),(str).length())
```

Побачили `c2stlstr()` — значить, робиться копія, зазвичай тому, що значення от-от віддадуть
сесії на іншому потоці, де приймальний буфер уже недійсний ([3.1](07-sip-stack-overview.md)).

> [!WARNING]
> `cstring::operator==` порівнює лише до **коротшої** з двох довжин:
> ```cpp
> bool operator == (const char* rhs_str) {
>   unsigned int rhs_len = strlen(rhs_str);
>   return memcmp(rhs_str,s,len <= rhs_len ? len : rhs_len) == 0;
> }
> ```
> Самі довжини він не порівнює ніколи. Тому `cstring` зі значенням `"INVITEX"` дорівнює
> `"INVITE"`, і зі значенням `"INV"` — теж. Будь-який код, що використовує `==` для безпекового
> чи маршрутного рішення, мусить перевіряти `len` самостійно. Це префіксне порівняння в костюмі
> оператора рівності, і на ньому вже спотикались.

## `sip_msg`

```cpp
struct sip_msg
{
    char*   buf;
    int     len;
    // Request or Reply?
    int     type;
    ...
};
```

Повідомлення володіє рівно однією річчю — `buf`. Усе інше є view в нього. `type` — це
`SIP_UNKNOWN`, `SIP_REQUEST` або `SIP_REPLY`, і за ним висить те, що цікавить:

```cpp
struct sip_request
{
    enum {
	OTHER_METHOD=0,
	INVITE,
	ACK,
        PRACK,
	OPTIONS,
	BYE,
	CANCEL,
	REGISTER
    };
    cstring  method_str;
    int      method;
    cstring  ruri_str;
    sip_uri  ruri;
};

struct sip_reply
{
    int     code;
    cstring reason;
};
```

Зверніть увагу: метод зберігається **двічі** — цілим для гарячого шляху і `cstring` для всього
іншого. `OTHER_METHOD` покриває все, чого немає в enum: `INFO`, `UPDATE`, `REFER`, `SUBSCRIBE`,
`NOTIFY`, `MESSAGE`. Саме тому вони диспетчеряться порівнянням рядків і трохи дорожчі в обробці.

Цей enum варто читати як заяву про наміри: ці сім методів — те, щодо чого сам стек має думку.
Усе інше переноситься сумлінно і лишається рівням вище.

## Ліниве розбирання заголовків

Заголовки спершу ідентифікуються, і лише потім розбираються. `parse_header.h` оголошує ті, що
цікавлять стек:

```cpp
	H_UNPARSED=0,
	H_TO,
	H_VIA,
	H_FROM,
	H_CSEQ,
        H_RSEQ,
        H_RACK,
	H_ROUTE,
	H_CALL_ID,
	H_CONTACT,
        H_REQUIRE,
	H_RECORD_ROUTE,
	H_CONTENT_TYPE,
	H_CONTENT_LENGTH,
	H_MAX_FORWARDS,
	...
```

`H_UNPARSED` — значення за замовчуванням, і більшість заголовків такими й лишаються. Заголовок,
до якого стеку немає діла — `User-Agent`, `P-Asserted-Identity`, будь-який `X-` — записується як
пара «ім'я/значення» і структурно не розбирається ніколи. Окремі файли `parse_*.cpp`
(`parse_from_to`, `parse_via`, `parse_cseq`, `parse_route`, `parse_uri`, `parse_nameaddr`,
`parse_100rel`, …) виконуються лише для тих заголовків, яким потрібна структура, і лише тоді,
коли ця структура знадобилась.

Це той самий інстинкт, що й ліниве розбирання в Kamailio, і з тієї ж причини: проксі чи B2BUA
чіпає жменю заголовків на повідомлення і не має платити за розуміння інших двадцяти.

## Асинхронний парсер

Датаграмні транспорти дають ціле повідомлення за одне читання. Потокові — ні, тож `tcp_trsp`
мусить знати, де повідомлення закінчується, перш ніж щось віддавати в `sip_parser`. Цим і є
`sip_parser_async.*`:

```cpp
struct parser_state
{
  char* orig_buf;
  char* c;         // cursor
  char* beg;       // last marker for field start
  int stage;
  int st;          // parser state (within stage)
  int saved_st;    // saved parser state (within stage)
  sip_header hdr;  // temporary header struct
  int content_len; // detected body content-length
  ...
  int get_msg_len() {
    return c - orig_buf + content_len;
  }
};

int skip_sip_msg_async(parser_state* pst, char* end);
```

`skip_sip_msg_async()` просувається настільки, наскільки дозволяють дані, і повертається; стан
переживає в `parser_state`, тож наступний шматок продовжує рівно з місця зупинки. `stage`
відстежує, у якій частині повідомлення ми перебуваємо, `st`/`saved_st` — позицію всередині
поточного заголовка.

Задача функції свідомо мінімальна — знайти кінець повідомлення. Вона читає рівно настільки, щоб
дістати `Content-Length`, після чого `get_msg_len()` дає повний розмір. Щойно стільки байтів
приїхало, буфер віддається справжньому парсеру.

> [!NOTE]
> Тому на потокових транспортах `Content-Length` є несучим так, як не є на UDP: пір, який про
> нього збрехав, десинхронізує потік. Це відома поверхня атаки для SIP-over-TCP і одна з причин,
> чому парсер варто фазити ([10.3](39-security-hardening.md)).

## Некоректні повідомлення

Повідомлення, яке не розібралось, відкидається на транспортному рівні, ще до появи будь-якої
транзакції, і логується. Воно ніколи не доходить до сесії, тож жодний код застосунку ним не
обдуриш — поверхнею атаки для некоректного повідомлення є сам парсер, а не застосунок.

Це правильний дизайн, і водночас саме тому парсер є найціннішою мішенню для фазингу в усьому
дереві: він досяжний неавтентифікованим пакетом, написаний на C поверх сирих вказівників, і все
нижче за течією довіряє його результату.

## Правила роботи з розібраними повідомленнями

- **`cstring` дійсний рівно доти, доки дійсний його `sip_msg`.** Копіюйте через `c2stlstr()`,
  якщо значення має пережити виклик.
- **Не робіть `==` над `cstring` для рішень, які мають значення.** Порівнюйте ще й `len`.
- **`method` — для семи відомих методів, `method_str` — для всього іншого.** Не перевіряйте
  `method == OTHER_METHOD` і не припускайте після цього нічого.
- **Додати структурно розбираний заголовок означає новий `parse_*.cpp` і новий `H_`-ідентифікатор.**
  Записати заголовок, який треба лише прочитати або переслати, не потребує ні того, ні іншого.
